# 言語サーバーの初期解析高速化と解析キャッシュ整理

状態: 設計承認済み。実装計画をレビュー中。以下は実装予定であり、現在の提供機能の説明ではない。

## 目的と優先順位

既存のAXEL構文、LSP応答、診断内容を維持し、実際の利用環境で初期解析の待ち時間を短縮する。利用者からは、調査結果に基づく改善対象の選定と、WorkspaceIndexのキャッシュ管理・依存関係探索を整理する方針について了承を得ている。その後に報告された初期解析30〜40秒を最優先に扱う。

1. 大規模文書と依存ヘッダーの初期解析に必要な処理量を減らす。
2. 変更のない解析結果の再利用を増やし、更新・破棄の責務を明確にする。
3. キャンセル、設定変更、編集中の不完全なソースに対する既存動作を維持する。

主な変更先はaxel-language-server。構文木そのものの誤りが判明した場合のみtree-sitter-axelで修正する。拡張側に解析ロジックを移さない。

## 選択する方針

### 推奨: 現在の解析パイプライン内で重複処理を減らす

構文木の世代内再利用と、原文・展開後ソースの処理責務を整理する。まずCPU負荷の高い処理を限定して変更し、同じ入出力で効果を測る。その後、可視宣言や型入力を再利用するためのキャッシュ管理を整理する。

別案のキャッシュ失効範囲の改善だけでは、キャッシュのない初回起動に対する効果が限られる。別案のワーカー導入・永続キャッシュ・増分パースは、状態共有や互換性への影響が広いため今回の初回実装には含めない。

## 設計

### 1. 構文木アクセスと世代管理

対象: cachedSyntaxNode.ts、documentAnalyzer.ts、typeChecking/syntax.ts、および測定で重複走査が確認された呼び出し元。

Tree-sitterを構文の唯一の正本とし、現在の読み取り専用アダプターを改善する。子ノード列挙、namedChildren、フィールド参照、同じ種類の子孫検索で既に取得した情報を再利用する。ネイティブとの往復を減らすために別の文法解釈を実装しない。

キャッシュは解析世代と実際のソースに所属させる。同一URI・versionでも原文、条件付き解析用ソース、マクロ展開後ソースを混同しない。型スナップショットの再利用は構文木だけでなく、曖昧構文からの回復結果が一致することを条件とする。

子孫検索の順序・範囲指定・匿名ノード・欠落ノード・parent関係・フィールドの対応を維持する。原文と展開後の位置対応も維持する。新しい共有索引を導入する場合は一度の走査で必要な索引を作り、用途ごとの全木走査が増えない構成にする。小さな文書や単発検索で逆効果になる事前計算は採用しない。

### 2. 原文と展開後ソースの解析処理

対象: documentAnalyzer.ts、macroReparse.ts、および必要な補助解析器。

依存関係の収集、原文に基づく情報の収集、展開後の宣言・型解析、最終結果の生成を明確に分ける。同じ原文由来の情報を先行解析、文脈付き解析、マクロ再解析で繰り返し作成している場合は、条件が同じ成果物を共有する。

条件付きinclude、マクロの可視位置、undef、GUIの既知型、起動スクリプトからの宣言は意味解析の入力である。これらが異なる解析結果は共有しない。単に最初の解析結果を返したり、診断処理を省略したりして待ち時間を短く見せない。

既存の同期・非同期APIは同じgeneratorを実行し続ける。新たな重いループも協調的キャンセルの境界を維持する。未完了の解析結果を完成したキャッシュとして公開しない。

### 3. WorkspaceIndexの派生キャッシュ

対象: workspaceIndex.tsと、必要な場合は解析世代・派生キャッシュを管理する小さな内部モジュール。

可視文書・可視宣言の収集結果を、依存関係と解析世代が変わらない間は再利用する。semantic tokens、型入力、呼び出し解決、文書コメント解析が各々同じ依存関係を探索し直さない構造を目指す。

初期解析の効果を測定した後、失効操作を一か所にまとめ、通常の文書変更では自身と影響を受ける依存元の派生結果を破棄する。設定、強制include、起動スクリプトなど広域に影響する変更は必要な全体失効を維持する。

失効対象にはincludeグラフだけでなく、未解決includeの候補、診断用依存関係、_login.axl、強制include、組込みカタログを含める。文書のclose、削除、rename、バックグラウンド処理のrollbackも同じ規則に従わせる。対応できない失効経路を残して部分失効を有効にしない。

## 互換性と失敗時の扱い

LSPインターフェース、設定名、既定値、公開解析APIは変更しない。診断・宣言・参照・トークンの内容とソース位置を保持する。キャンセルやContentModifiedで古い解析世代を公開しない。キャッシュ保持によるメモリ増大を避け、世代交代と文書closeで不要な参照を解放する。

対象ファイルの復号方法は性能測定の入力条件として固定する。依存ファイルの現在の読み込み実装はUTF-8である。文字コード対応の仕様変更は今回の高速化に混ぜない。

## 検証と成功条件

1. 実装前に、上記の実ファイル・設定・Shift_JIS入力を指定できる任意実行の外部性能テストを用意する。標準CIは外部インストールを必要としない。
2. 新規プロセスで初期診断までの時間、解析完了後の再要求時間、解析対象数を測る。実装前後とも3回測定し中央値を比較する。再計測時には性能測定を並列実行しない。
3. 初回診断時間の中央値を25%以上短縮することを目標にする。効果は実測値で報告し、満たさない場合は未達として残る支配的処理を示す。
4. 同じ入力の診断内容と位置を比較する。件数一致だけでは合格にしない。合成fixtureでは宣言・参照・GUI・マクロ展開後の位置も比較する。
5. 大規模GUI、強制include、_login.axl、多段include、マクロ展開を含む合成fixtureで、重複走査や再計算の回数を検証する。小規模文書でも新たな全走査が増えていないことを確認する。
6. 未解決ヘッダーの新規作成、依存先の編集・削除・rename、設定変更、編集中の不完全構文、キャンセル後の再要求で古い結果が返らないことを検証する。
7. npm run test:ci（lint、unit、integration、e2e、performance）を実行する。既存の編集応答時間・キャッシュ再利用・キャンセルの検証を維持する。
8. 大きな文書の複数回編集とclose後に古い世代が保持され続けないことを確認する。CPUプロファイル取得は時間比較用の通常実行と分ける。

## ドキュメントへの影響

docs/developer/cancellation.mdに記載された解析パイプライン、共有状態、rollbackの説明が変更対象になる。最終実装に合わせて必要な箇所を更新する。新しい測定手順は開発者向け資料に記載する。LSP動作・設定が変わらなければユーザーマニュアルの変更は不要。

この設計書は実装仕様の提案として分離する。既存の開発者資料を、まだ実装していない動作の説明に置き換えない。
