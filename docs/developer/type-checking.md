# Type-checking architecture and verification

Startup globals use `loginScope.ts` and a separate WorkspaceIndex with startup sharing disabled. Its cached TypeContext retains private aliases and original class identity. Consumer contexts import only the published bindings/classes/functions; startup `main` and macro names are excluded. Ordinary source/include bindings precede startup bindings. File or configuration changes invalidate the snapshot and consumer caches without dropping unsaved source inputs. See [startup support](../user/login-scope.md) for the client notification contract.

[Syntax recovery](../../src/analyzer/syntaxRecovery.ts) records affected statement/declaration ranges and dependent reference ranges in each document analysis. It traverses Tree-sitter error paths, respects inactive and recovered macro ranges, and conservatively widens suppression to a scope when declaration names or scope boundaries are unavailable. Semantic reference checks, GUI receiver checks and published type diagnostics use this metadata instead of disabling semantic checks for the whole file. Declaration dependencies are tracked within the analyzed document; this metadata does not establish that unresolved includes or external declarations are complete.

[General macro reparsing](../../src/analyzer/macroReparse.ts) expands visible object-like and function-like macros into a virtual source and reparses that source with Tree-sitter, including valid-looking invocations, statements, expressions and generated declarations. The [expander](../../src/analyzer/macroExpansion.ts) skips directive bodies, literals and comments and respects visibility, inactive/uncertain regions, `#undef` and bounded recursion. Function-like macro stringification (`#parameter`) uses the written argument before expansion, collapses comments and whitespace outside literals, and escapes the resulting string literal. Ordinary occurrences of the same parameter continue through normal expansion. Expansion errors or truncation retain the original invocation for existing diagnostics. The analyzer maps locations back to the written source; generated tokens point to their invocation, while unchanged source keeps its original position. Shared type-snapshot nodes retain their identity. Input include-symbol ranges and macro visibility positions are mapped into virtual coordinates before reparsing. Written macro names and argument references are retained separately for hover, signature help, navigation and rename. Semantic tokens prioritize the written macro name over expansion-generated functions or members at the same location and retain written argument tokens. Invocation hover also expands object-like aliases used as calls (for example, `#define CDSPRINT printf`), showing the original definition, documentation and definition origin alongside the expanded call. Preprocessor directives continue through the existing preprocessor analysis; NULL provenance and symbolic system values continue through their existing context-aware handling.

`F(&item);` and `T(*item);` can have declaration-shaped trees because AXEL permits parenthesized pointer declarations. [Call disambiguation](../../src/analyzer/ambiguousCalls.ts) resolves a visible function or method in the current document's lexical scopes, including definitions later in the file, before reparsing the statement in an expression context. Tree-sitter supplies the call and argument nodes; source ranges are preserved, false declarations are removed, and normal argument diagnostics apply. Type names retain their declaration interpretation.

Preprocessor directive operands are marked separately in reference data. Ordinary semantic diagnostics exclude those references, and expression type checking skips conditional directive operands. Undefined identifiers in `#if`, `#elif`, `#ifdef`, and `#ifndef` do not produce unknown-identifier errors; active branch bodies retain ordinary diagnostics. Macro references remain available to navigation and highlighting.

## Ownership and data flow

Tree-sitter remains the authoritative syntax parser. [DocumentAnalyzer](../../src/analyzer/documentAnalyzer.ts) copies the final macro-expanded parse into a document-generation-local [type snapshot](../../src/analyzer/typeChecking/syntax.ts); native nodes are not retained across edits. [WorkspaceIndex](../../src/analyzer/workspaceIndex.ts) supplies definite visible documents, position-aware macros, and the builtin catalog before aggregating type diagnostics with existing diagnostics and applying the configured problem limit.

[Declaration resolution](../../src/analyzer/typeChecking/declarations.ts) first creates lexical scopes and class identities, then resolves bindings, signatures, aliases, and declarator shapes. Forward declarations and their definitions share an identity in the same scope. Inactive and uncertain declaration subtrees are excluded. Class roles come from a normalized declaration URI and exact declared name in the [catalog](../../src/analyzer/typeChecking/builtinCatalog.ts), and resolve onto the selected class identity. Never apply builtin rules by comparing an unresolved type-name string.

[Compatibility](../../src/analyzer/typeChecking/compatibility.ts) is a direct relation parameterized by use site. Numeric conversions, user conversion methods, initialization, assignment, arguments, and returns have different rules. Do not search a conversion graph: a class conversion to `int` plus a numeric conversion from `int` to `double` does not imply a class-to-`double` conversion. [Expression analysis](../../src/analyzer/typeChecking/expressions.ts) uses storage/temporary/reference categories and callable candidates; [diagnostics](../../src/analyzer/typeChecking/diagnostics.ts) checks statements and declaration restrictions.

`ExpressionResult.constant` contains an evaluated value only when known. `constantExpression` records that an expression qualifies as constant without inventing a value. In particular, `sizeof` can satisfy an integer constant-expression requirement without the server assuming a runtime size. Preserve this distinction when composing expressions; an arbitrary placeholder integer would corrupt duplicate-case checks and constant evaluation.

Builtin behavior follows the observed AXEL 510 / SX-Meister 20.0.0 Windows profile. Registered editor declarations may contain prototypes or omit runtime restrictions. Their signatures support lookup, but they are exempt from executable-source type diagnostics. Header syntax belongs in the parser; runtime conversion and operator rules belong in this server. Correct erroneous analysis headers instead of emulating C++ behavior downstream.

## Catalog and invalidation contract

The companion format and client setup are described in the [user guide](../user/type-checking.md). `loadBuiltinCatalog` validates each companion atomically: schema version 1, profile `axel-510`, explicit existing relative declaration files, and role bindings to those files. Absolute paths, escaped paths, external symlink targets, conflicting bindings, and unknown profiles fail closed. A failed companion contributes an issue to the returned catalog instead of granting partial exemptions. Valid independent companions remain usable.

The `analysisOnlyMacros` field accepts `[]` or a list containing `NULL`. Opting into `NULL` identifies helper definitions from the entry and its exact declaration allowlist; expression type analysis ignores those legacy helper definitions. It does not ignore a user-source redefinition or exempt an unrelated forced include. Shipped analysis headers should use AXEL's builtin `NULL` token instead of defining it as integer zero. Source definitions and `#undef` must retain position and origin, and conditional evaluation and expression analysis must agree on the visible definition.

General declaration lookup in `resolution.ts` indexes names, containers and inherited members once per pair of local and visible declaration arrays. These arrays and their declaration objects represent immutable analysis generations: replace them when declarations change rather than mutating published entries. WeakMap keys release old generations; changing the visible array invalidates lookup even at an unchanged document version. Returned lookup arrays are copies so callers cannot modify cached results.

[Call resolution](../../src/analyzer/typeChecking/callResolution.ts) reuses diagnostic context construction and argument compatibility for explicitly registered builtin declarations. A common result type is sufficient for expression diagnostics but never proves a unique navigation target. Hover, definitions and signature help expose all remaining declarations; unique-target operations do not choose an arbitrary candidate. Ordinary user calls retain arity-based resolution. Qualified static calls resolve their owner through the same class lookup as other type analysis.

Workspace call resolvers are created lazily and cached by source/dependency analysis generations, startup documents and builtin catalog identity. Configuration and file invalidation clear the cache. Expanded calls use virtual syntax and map declaration positions back to written sources; written macro names retain macro navigation. [Feature agreement tests](../../src/test/integration/features/overloadFeatureAgreement.test.ts) and [LSP tests](../../src/test/e2e/overloadResolution.test.ts) cover selection and edits.

[GUI reference resolution](../../src/analyzer/guiReferenceResolution.ts) owns implicit GUI member selection: the enclosing event receiver, named part paths, inherited declarations, dialog-owner fallback, and precedence relative to local names and explicit type receivers. Hover and navigation consume the same result; references, rename and signature help use navigation's selected declaration. Semantic tokens, implicit member completion, and semantic name/argument-count checks also use this resolver. Membership comes from parsed declaration ownership and base-class links. Display text and proximity to a preceding class never assign an unowned declaration to a class, including static declarations. If malformed source does not establish membership, member lookup remains unresolved; ordinary global lookup can still resolve a bare reference.

Within inline and external GUI event bodies, the shared GUI context supplies the component class as the type of `this`. Name resolution and expression type checking then apply ordinary member, inheritance, assignment and argument rules. GUI type names do not exempt missing members from diagnostics, and declarations in unrelated classes do not establish that a bare name is valid. Event declaration names remain indexed for override navigation; the unresolved-use diagnostic excludes these declaration positions.

Written references retained after macro expansion must pass through the same GUI resolution as ordinary references; only the written macro name uses macro-specific navigation. Token lookup caches must preserve GUI class/document lookup methods so included GUI receivers resolve consistently. They reuse dependency document lists only within one token request. GUI context lookup checks event ranges before resolving receivers and searches local classes before loading dependency documents. [Feature agreement tests](../../src/test/integration/features/guiMacroNavigation.test.ts) cover macro expansion, inheritance, local shadowing, nested member paths, included GUI receivers and bounded dependency lookups.

Macro reparsing retains the expanded analysis in `expandedSource`. Semantic and type diagnostics resolve names using virtual source positions and map only the resulting diagnostic ranges back to the written document. Mapping scopes and GUI events to an invocation before resolving names would merge distinct event bodies and local declarations. Inline GUI events therefore also establish function scopes for their parameters and locals. [Macro reparsing tests](../../src/test/integration/features/macroReparse.test.ts) cover included GUI macros and ensure genuine errors inside expansions are still reported at the invocation.

Native syntax getters and field lookups are cached by a read-only [syntax view](../../src/analyzer/cachedSyntaxNode.ts). Source text and document version identify a cached tree; changing visible context still recomputes analysis. Workspace analysis releases these native views after final diagnostics, and edits or explicit clearing discard previous generations. Published snapshots contain copied data rather than native nodes.

Before resolving includes, the workspace collects dependency metadata without building reference indexes or type snapshots. While headers are being indexed in the background, diagnostic requests can already report missing unconditional includes. Final diagnostics also place unresolved includes before body diagnostics so diagnostic count limits do not displace them as semantic results arrive. Conditional includes retain their original syntax-tree provenance through branch recovery and macro reparsing and wait for header macro context before being reported. A foreground analysis already available for the same version is reused. Cyclic includes promote this preliminary analysis using the open document's current text so included documents can resolve its declarations. Repeated include paths are resolved once per macro lookup operation, retaining occurrence order and position-dependent visibility; later operations check the filesystem again. Macro source-location mapping uses ordered segment lookup, preserving start/end boundary semantics for empty and adjacent expansions. Scope IDs, scoped names and macro names are indexed within immutable analysis generations.

Document versions alone do not identify an analysis context. Changes in visible includes, macros, forced entries, configuration, and notified companion/declaration files invalidate dependent results. Catalog registration must never exempt all forced includes or all headers with a familiar basename. Regressions must exercise unchanged source versions with changed dependencies as well as normal edits.

## Regression coverage

The checked-in [corpus manifest](../../src/test/integration/fixtures/type-checking/manifest.json) fixes source hashes, expected compiler errors, error codes, and evidence identifiers for 156 ordinary cases and one separately tracked compiler crash. A crash has `expectedError: null`; it is not an accepted program or an ordinary type error. The corpus covers the initial observations and their follow-up experiments, rather than asserting complete equivalence with AXEL.

The [conformance suite](../../src/test/integration/features/typeCheckingConformance.test.ts) runs 135 selected ordinary cases through the actual analyzer and workspace diagnostics. The 21 redundant ordinary cases remain as evidence; the selection and reasons are explicit in [the corpus helper](../../src/test/support/typeCheckingCorpus.ts). Small handwritten registered headers make ordinary CI independent of product header copies and an installed AXEL runtime. [Declaration tests](../../src/test/integration/features/typeDeclarationResolution.test.ts), [operator and overload tests](../../src/test/integration/features/typeCheckingOverloads.test.ts), and [context invalidation tests](../../src/test/integration/features/typeCheckingContext.test.ts) cover supporting behavior beyond the corpus. Parser grammar contracts belong in tree-sitter-axel; server regressions assert diagnostics and feature results from actual source.

```sh
npm run test:unit -- --grep "Type checking"
npm run test:integration -- --grep "Type checking"
```

Ordinary checks do not start AXEL. Successful corpus checks establish agreement with those recorded expectations only; unsupported generalizations and different runtime versions need new evidence and regression cases.

Conditional syntax recovery runs before semantic indexing when the original Tree-sitter tree has errors. `conditionalReparse.ts` lexes directive boundaries outside comments and literals, masks ordinary code, and lets Tree-sitter parse the directives. The existing preprocessor evaluator supplies branch activity and source ranges; it does not depend on the broken AXEL brace structure. Definite inactive code and resolved conditional directives are replaced with spaces while preserving UTF-16 offsets and line endings, then Tree-sitter parses the resulting AXEL source. Uncertain conditional groups and malformed directive trees are left unresolved. Ordinary syntax-valid documents retain the normal parsing path.

## Document changes and request ordering

The LSP layer applies text changes immediately through `TextDocuments`, but coalesces foreground indexing by URI in a fixed 20 ms window starting at the first pending change. The timer is not extended by later edits. Before a document request is analyzed, all pending open-document changes are indexed synchronously, including changes in other documents that may supply declarations. Requests therefore do not wait for the timer, and edits separated by requests remain observable in order. Opening a document indexes it immediately; closing it discards pending work, and shutdown clears the timer. The window is a scheduling delay, not a bound on analysis duration: parsing and indexing still run synchronously, and a request can wait for pending changes in other documents.

Dependency indexing retains declarations, type snapshots and syntax diagnostics, but does not run body type/semantic diagnostics for unopened dependencies. `workspaceIndexComplete` records completion of dependency context analysis independently of `workspaceDiagnosticsComplete`. Explicit `indexDiskDocument` and open-document diagnostic requests still compute and cache full diagnostics. Consumers of `getAnalyzedDocument` must not assume an indexed dependency already has full diagnostics.

Include resolutions are shared across nested passes within one synchronous indexing or diagnostic operation, including a background indexing job. A background job owns its resolution cache, but installs it only while executing a step; interleaved requests use independent caches. Completion, cancellation and errors discard the job cache. It is not retained across requests or background jobs. Subsequent operations therefore recheck missing files and search paths without depending on watcher delivery.

Background dependency and startup indexing use the same generator-based traversal as synchronous indexing. Each step returns to the event loop before another file or context-analysis phase; this includes open dependency headers. Editing, invalidation, configuration changes and synchronous indexing requests invalidate suspended work before it resumes. Pending cyclic-include inputs belong to the traversal, rather than shared workspace state. Diagnostic requests may return provisional syntax/include results until background completion triggers refresh. Individual file parsing, context analysis and body diagnostics remain synchronous and can still cause noticeable pauses.
